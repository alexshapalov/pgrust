# PGX v0.1 baseline

The measured state of PGX at the v0.1 freeze: one PgRust runtime holding
many short-lived Postgres-compatible databases on Linux/ZFS. Every number
below has a script and a raw result in the repository
(`benchmarks/pgx/linux/README.md`). Method and discussion are in
`linux-results.md` and the focused documents it links.

## Build, host, profile

| | |
|---|---|
| Branch | `pgx-experimental-plan` |
| Engine baseline | `727f31e49f` (last engine change; recorded with the freeze commit in `v0.1-readiness.md`) |
| PGX profile | `configs/pgx-ephemeral.conf` as of `696318b79e` (documented in `phase1a-config.md`) |
| Host | OVH VPS `vps-d2a3c460`: 4 vCPU x86_64, 7.6 GiB RAM, no swap, 25 GB root + 48.9 GiB ZFS partition, $8.50/month (`linux-host.md`) |
| Storage | ZFS 2.4, recordsize 128K, compression off, block cloning on, ARC capped at 1 GiB; `file_copy_method = clone` |
| Isolation during runs | 6 GiB no-swap cgroup per run; host never swapped |
| Load generator | on the same 4 vCPUs as the server, so these are architecture numbers, not capacity limits |

Most measurements were taken on the build named in each row. The builds
after them changed only memory retention and autovacuum scheduling. The
regression suite and the 30,000-lifecycle churn were re-run on
`727f31e49f` itself.

## Memory density

| | Runtime footprint (PSS) | Build |
|---|---|---|
| Runtime with no databases (janitor, sealed 50-table template, warm pool) | 85 MB | `dedfdf9ca5` |
| 1000 untouched idle databases | 128–155 MB | `dedfdf9ca5` |
| 1000 idle databases, each queried once | 213 MB (217 MB on `bb3a8ab54b`) | `0131cc9b12` |
| 1000 databases, 100 of them active | 283 MB (808 MB before the density fixes) | `dedfdf9ca5` |

Per database, on top of the runtime:

- **~70 KB for an untouched database.** Measured 43–70 KB; 70 KB is the
  planning figure. The spread between autovacuum settings at 1000
  databases (128 vs 155 MB) is not explained.
- **~128 KB once a session has queried it.** A query loads the database's
  relation and catalog caches lazily, and they stay for the database's
  life.

The 43 KB figure is the best case, an untouched database with autovacuum
at its default. Do not quote it as the production per-database cost.

Before this work, an idle database cost 550–580 KB and 1000 of them used
640–669 MB.

## Lifecycle memory (create → use → drop)

| Stage | Retained per lifecycle | Memory after 10,000 / 30,000 lifecycles |
|---|---|---|
| Before the fixes (`1781903578`) | ~11 KB, linear | 262 MB / — |
| After the lifecycle and density fixes (`60fca8427f`, run F) | ~0.9 KB, linear | 109 MB / 126 MB |
| After the shared `pg_database` cache fix (`727f31e49f`, run G) | ~0.2 KB, falling | 108 MB / 111 MB |

Growth per 100 lifecycles in the last quarter of the 30,000-lifecycle
runs:

- **Run F (before the last fix):** 0.093 MB, and not falling.
- **Run G (after it):** 0.020 MB, falling each quarter (0.129 → 0.053 →
  0.014 → 0.020).

PGX no longer has the large linear lifecycle leak seen earlier. A small
residual retention of about 0.2 KB per lifecycle remains: about 2 MB per
10,000 lifecycles. Memory is not perfectly flat. The tracker build puts
most of the remainder in small per-session strings (the data-directory
and database paths) and query-descriptor slots. Raw data:
`linux-churn.md`, runs A–G.

### The last fix: stale `pg_database` rows in the shared catalog cache

- **Cause.** DROP DATABASE removed the dropped database's own cache
  entries (keyed by its oid as the owning database). It left behind that
  database's `pg_database` row in the shared catalog cache, which is keyed
  by the database oid under the shared-catalog owner. Nothing looks up a
  dropped oid again, so the entry stayed until the cache's global budget
  of 262,144 entries evicted it.
- **Size.** About 2 stale entries per lifecycle, because two generations
  of the entry are kept. The `pg_database`-by-oid cache grew from 324 to
  14,529 entries over 72 churn cycles, all of them stale.
- **Fix.** DROP DATABASE now also removes the dropped database's
  `DATABASEOID` entry from the shared cache (`727f31e49f`, with a unit
  test).
- **How it was found.** A cache census in the `pgrust: memctx` debug
  report (`4cefb2fc05`) counts entries per cache, shared or per-database,
  and how many are at a superseded generation. It stays in the build for
  future investigations.

## Executor memory lifetime fixes (DML)

Three DML paths kept one tuple copy, and for UPDATE a column bitmap, per
row until the statement ended. Memory therefore grew with row count.
Measured with `insert-memory-repro.py` (statement-level peak above the
idle runtime) and the memory-heavy workloads in `limits.py`:

| Statement | Before | After (`d48f587da0`) |
|---|---|---|
| INSERT…SELECT through a projection, 1 / 2 / 3M rows | +59 / ~+290 MB / refused at the 256 MB session limit | 63 / 85 / 89 MB |
| Whole-table UPDATE (every row), 1 / 2 / 3M rows | 98 / 261 / 400 MB | 1 / 3 / 11 MB |
| `INSERT INTO t SELECT * FROM big` (the `large_insert` workload) | refused at 321 MB | completes, 76 MB peak |

- **INSERT…SELECT** stays at 85–89 MB from 2 to 3M rows. It no longer
  scales with row count; the rest is the source scan and the target's
  buffers.
- **UPDATE, MERGE UPDATE and ON CONFLICT DO UPDATE** share one fix.
  Their memory is essentially independent of row count.

Commits:

- `ea6d055cb2`: INSERT…SELECT through a projection.
- `daf827c0ff`: UPDATE, MERGE UPDATE, ON CONFLICT DO UPDATE.
- `67269453b2`: unprojected INSERT…SELECT.
- `d48f587da0`: corrects a regression in the previous two. A virtual slot's
  buffer was reused across rows, which corrupted multi-row INSERT into a
  partitioned table. The regression suite caught it before anything else
  was built on it.

## Memory limits

Three nested limits, each refusing with SQLSTATE 53200 and a hint:

```
session limit  (pgrust.session_memory_limit, e.g. 256 MB)
  ↓
database limit (pgrust.database_memory_limit, 2–4× the session limit)
  ↓
runtime limit  (pgrust.runtime_memory_limit, 70–80 % of the cgroup's memory.max)
  ↓
Linux cgroup memory.max: the hard boundary
```

Under a 256 MB session limit (`results/vps-d2a3c460-d48f587da0/limits/workloads.json`):

- **Refused with 53200:** in-memory sort, hash join, hash aggregate,
  materialized CTE, `json_agg`, `array_agg`, when they exceed the limit.
- **Complete:** COPY IN, COPY OUT, large INSERT…SELECT, CREATE INDEX,
  rewriting ALTER TABLE, spilling sort.
- **After a refusal:** the session stays usable, its database and every
  other database stay usable, a bystander database querying every 50 ms
  sees 0 errors, and the runtime does not panic. The one panic path found,
  a sort-growth `expect`, was fixed in `dde6c13de4`.
- **cgroup backstop:** under a 1 GiB `memory.max` without the PgRust
  runtime limit, a runaway query gets the runtime OOM-killed. The host
  and unrelated services survive. With `pgrust.runtime_memory_limit = 700`
  the query is refused first (peak 674–676 MB, 0 OOM kills).

## Compatibility

- **Regression suite:** 219 of 231 byte-exact on `727f31e49f`
  (`results/vps-d2a3c460-727f31e49f/regress`). All 12 differing tests differ in query-plan
  (EXPLAIN) text only. That is 12 known plan-output differences, with 0
  observed result differences. The same 219 / 231 holds on every final
  build and with the final profile defaults.
- **Frameworks:** 36 / 36 runs pass on `60fca8427f` (engine `6fe0b1ad65`):
  Django, node-postgres, SQLAlchemy, Prisma, Rails-shaped SQL and a real
  Rails 8.1.4 app on Ruby 3.3.8, 3 runs each on PGX and PostgreSQL 18
  (`agent-workloads.md`).
  - Real Rails covers `db:prepare` with migrations (FKs, unique and
    composite indexes, jsonb with GIN), model tests with fixtures,
    database-raised `RecordNotUnique` / `InvalidForeignKey`, a savepoint
    rollback, a schema-changing migration, `db:schema:load`, and tests
    after each schema change.
  - Real Rails is within 0–5 % of PostgreSQL 18 in every tested phase.
    That holds for this lifecycle workload; it is not a general speed
    claim.

## Query performance (`linux-query-performance.md`, `dedfdf9ca5`)

| | PGX vs PostgreSQL 18 |
|---|---|
| Point SELECT by primary key | 0.25 vs 0.13 ms (1.9×); 0.18 ms (1.4×) with a 128 MB buffer pool |
| Single-threaded large scans (500k-row aggregate) | 1.5–2.2× slower |
| Large scans with the PgRust runtime and parallel query | faster (36 vs 58 ms), at +95 MB of memory |
| COPY | equal |
| CREATE INDEX | 1.1–1.3× slower |
| Point SELECT throughput, 4 clients | equal or higher (7,878 vs 7,662 /s) |
| Whole framework lifecycles | 0–15 % slower; node-postgres 17 % faster |
| Real Rails lifecycle | within 0–5 % |

Profile versus engine:

- **Profile.** Part of the point-SELECT gap is the PGX profile's small
  buffer pool; raising it to 128 MB takes 0.25 to 0.18 ms.
- **Engine.** The rest is per-statement engine overhead, 0.05–0.15 ms.

PGX is not generally faster than PostgreSQL and does not need to be. The
product numbers are density, mint time and branch storage.

## Autovacuum profile

Profile defaults:

- `pgrust.autovacuum_skip_idle_databases = on`: databases with no writes
  since the last visit are skipped.
- `autovacuum_naptime = 300`.

| 1000 idle databases | Idle CPU (one core) |
|---|---|
| Stock autovacuum | 5.4–6.7 % |
| Profile defaults | 0.33 % (`0131cc9b12`), 0.43 % (`bb3a8ab54b`) |
| Autovacuum off | 0.22 % |

- **Fairness.** Written databases must still be vacuumed and analyzed
  when most databases are idle. Before `6fe0b1ad65`, skipped databases
  never advanced their last-visit time and always won the oldest-first
  choice, starving databases that changed. Validated with 5 written
  databases among 50 idle ones: all 5 vacuumed and analyzed within 4 s,
  and revisited 6 s after new writes (`skipidle-check.py`).
- **First pass.** Right after all 1000 databases have been written, idle
  CPU is 1.5–2.9 % while autovacuum makes its first pass.

## Branch storage (ZFS copy-on-write, recordsize 128K)

| Template (logical) | Clone mint p50 | Physical per new branch |
|---|---|---|
| 1.0 GB | 135 ms | 2.3 MB |
| 2.0 GB | 198 ms | 3.7 MB |
| 5.2 GB | 417 ms | 7.0 MB |
| 10.1 GB | 674 ms | 13.6 MB |

A 10 GB database can produce an isolated copy-on-write branch in about
674 ms, initially consuming about 13.6 MB of additional physical storage.
COW branches initially use hundreds of times less physical storage than
full-copy branches. A full copy of a 674 MB template takes 933 ms against
113 ms for a clone.

### Recordsize trade-off (1 GB template, `zfs-cow.md`)

| Recordsize | Clone mint | Fresh branch | 1000 scattered single-row updates |
|---|---|---|---|
| 128K | ~135 ms | ~2.3 MB | +420–505 MB |
| 16K | ~369 ms | ~11.1 MB | +65 MB |
| 8K | ~893 ms | ~20.4 MB | +33 MB |

- **128K is the v0.1 default** for disposable branches: the fastest and
  cheapest to create.
- **Its cost** is write amplification on scattered updates. Each dirtied
  page rewrites a whole 128 KB record, about 0.45 MB per updated row.
  Bulk inserts cost 1.1–1.2× their logical size.
- **16K or 8K** are candidates for a future write-heavy, long-lived branch
  profile. Not implemented in v0.1.

## Creating databases (`linux-mint.md`)

| | p50 | p95 | p99 |
|---|---|---|---|
| Warm mint (spare from the pool) | 6.2 ms | 8.5 ms | 9.4 ms |
| Cold mint (19 MB, ~600-file template) | 74 ms | 94.5 ms | 101.6 ms |
| Reconnect to an existing database (floor) | 3.8 ms | | |

- **Scope.** Times run from the client's connection to `SELECT 1`, at
  engine level over a Unix socket. They are not PGRun end-to-end numbers.
- **Cold mints.** Dominated by per-file ZFS cloning (57 of 60 ms); they
  drain at ~35–40 per second.
- **Bursts.** 500 simultaneous new-database requests complete with 0
  errors in 12.6–13.8 s.

## Active databases among 1000 (`linux-density.md`, `dedfdf9ca5`)

| Active databases | p50 | p99 | Server CPU | Footprint |
|---|---|---|---|---|
| 5 | 0.64 ms | 1.66 ms | 31 % | 135 MB |
| 20 | 0.64 ms | 2.44 ms | 97 % | 159 MB |
| 50 | 1.53 ms | 12.5 ms | 202 % | 205 MB |
| 100 | 15.6 ms | 45.8 ms | 201 % | 283 MB |

- **Errors.** 0 at every level.
- **Not a scalability limit.** Above ~50 active, the 4 vCPU host is
  CPU-bound with the load generator sharing it, and 100 active is a
  queueing figure. Capacity needs a larger host with a separate load
  generator.
- **Memory.** Active-database memory dropped from 808 MB to 283 MB at
  100 active.

## Host economics (measured/modelled small-host economics)

`economics.py` with the measured inputs above models one $8.50 host at
roughly 250 concurrent agent branches, at 20 % of their life active and
10 MB written each. CPU is the limit; memory alone would allow about
14,000. This is a model on a 4 vCPU host, not a guaranteed production
capacity. The assumptions and their sensitivity are in
`linux-pricing-economics.md`.
