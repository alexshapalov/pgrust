# PGX v0.1 readiness

**Decision: ready for PGRun beta integration as a disposable,
non-production database runtime.** PGX v0.1 is not a replacement for a
customer's production PostgreSQL.

## Approved use

PGX v0.1 is approved for PGRun as:

- ephemeral branch databases;
- CI databases;
- per-PR databases;
- agent databases;
- test databases;
- preview or staging-style disposable databases.

PGX v0.1 is **not** approved as:

- a customer's production primary database;
- a long-term system of record;
- a high-availability primary;
- a database that needs point-in-time recovery.

PGRun keeps the customer's production database where it is and gives PGX
only sanitized copies:

```
customer production PostgreSQL
        │
        │  sanitize / golden copy (PGRun Safe Copy)
        ▼
      PGRun ── golden templates, durable in object storage
        │
        ▼
    PGX runtime (one per host, in a cgroup)
   /     |      \
agent    CI      PR
 DB      DB      DB
```

Databases that PGX cannot serve take the standard PostgreSQL path
(`compatibility-gate.md`).

## READY

| Capability | Evidence |
|---|---|
| Shared runtime: 1000 databases in one process | 128–155 MB untouched, 213 MB queried once (`linux-density.md`) |
| Ephemeral databases (mint-on-connect, janitor reaping, pinning) | `ephemeral-databases.md`, `linux-mint.md` |
| Warm pool | warm mint p50 6.2 ms; 500-request burst with 0 errors |
| ZFS copy-on-write branches | 10 GB template: 674 ms, 13.6 MB physical (`zfs-cow.md`) |
| Memory limits (session / database / runtime) | 53200 refusals, session and bystanders unaffected (`linux-limits.md`) |
| cgroup isolation | runtime OOM-killed under 1 GiB `memory.max`; host and other services survive |
| Frameworks: real Rails 8.1, Django, Prisma, SQLAlchemy, node-postgres, Rails-shaped SQL | 36 / 36 (`agent-workloads.md`) |
| Large INSERT…SELECT and large UPDATE | memory flat in row count (`v0.1-baseline.md`) |
| Long churn | 30,000 lifecycles: 111 MB, ~0.2 KB each (`linux-churn.md`, run G) |
| Autovacuum profile | 1000 idle databases at 0.33–0.43 % of a core; written databases still serviced |
| Runtime status API | `pgrust_runtime_status()`, JSON (`pgrun-interface.md`) |
| Per-database connection limits | `pgrust.ephemeral_db_connection_limit`; caps a noisy neighbour's effect |

## Known limitations

- **Residual lifecycle retention.** About 0.2 KB per create → use → drop
  lifecycle (~20 MB per 100,000). Recycle runtimes by policy
  (`pgrun-interface.md`, "Runtime recycling").
- **12 plan-text regression differences.** 219 / 231 byte-exact; the 12
  others differ only in EXPLAIN output, with 0 observed result
  differences.
- **Single-statement latency.** Point SELECTs are 1.4–1.9× slower than
  PostgreSQL 18, about 0.05–0.15 ms more. Single-threaded large scans are
  1.5–2.2× slower. COPY and 4-client throughput are equal.
- **Write amplification at recordsize 128K.** Scattered single-row
  updates cost ~0.45 MB each on a branch; bulk writes cost 1.1–1.2×.
- **One crash domain.** A runtime crash, or an OOM kill at the cgroup
  limit, ends every database in that runtime. Running several runtimes
  per host trades ~35–55 MB each for smaller failure domains.
- **Not durable.** The profile runs `fsync = off` and
  `full_page_writes = off`. Branch data can be lost or corrupted on a host
  crash. Golden templates must be restorable from object storage, and that
  restore tooling is PGRun work that is not built yet.
- **Extensions.** Compatibility with PostgreSQL extensions is not
  universal and was not surveyed. Only what the regression suite and the
  framework workloads use was tested.
- **Cold mint floor.** About 60 ms of per-file ZFS cloning for a
  600-file template. The first session in a new database adds ~15 ms.
- **Capacity numbers come from a 4 vCPU host** with the load generator
  on the same CPUs. Production capacity has not been measured.
- **Not a production database.** PGX v0.1 is not intended as any
  customer's primary database (see "Approved use").

## Not a goal for v0.1

- replacing a production HA database;
- Neon-style distributed or remote storage;
- the full PostgreSQL extension ecosystem;
- zero-downtime compute migration;
- multi-region primaries;
- general-purpose production PostgreSQL replacement.

## After the freeze

Open-ended engine optimization stops here. The ~0.2 KB per lifecycle is
left alone unless one of these happens:

- it grows materially;
- it destabilizes a runtime;
- an obvious contained fix turns up.

Engineering moves to PGRun integration (`pgrun-integration.md`). The next
benchmark is the end-to-end one:

```
PGRun API request → host chosen → database allocated → credentials →
routing ready → DATABASE_URL returned → SELECT 1 succeeds
```

Targets: p50 < 500 ms, stretch p50 < 200 ms.
